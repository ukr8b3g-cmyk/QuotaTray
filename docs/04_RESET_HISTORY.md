# 04 リセット履歴・判定仕様

## 1. 目的

予定された週間リセット、他画面で使用されたリセット券、予定外の大幅回復を区別し、ローカル履歴として残す。

## 2. 観測モデル

観測ごとに最低限保存する候補：

- 観測成功時刻UTC
- 取得契機：poll / notification / panel-open / startup / resume / manual
- `limitId`
- primary/secondary識別
- `usedPercent`
- `windowDurationMins`
- `resetsAt`
- リセット券 `availableCount`
- 返された期限の一覧（IDは保存不要）
- `planType`（利用可能な場合）
- App Serverバージョン

画面用の最新値はメモリに保持する。ファイルには毎分書かず、次の場合だけ保存する。

- 使用率、リセット日時、券数、期限、プランが変化
- リセット候補を検出
- 30分ごとの限定チェックポイント
- アプリ終了前の最終状態

## 3. 発生時刻

リセットの正確なサーバー時刻が返らない場合：

```text
前回成功時刻 ～ 今回成功時刻
```

を発生範囲として保存する。通知で即時変化を受けても、表示は「検出時刻」とし、サーバー実行時刻と断定しない。

## 4. リセット候補の一次検出

同一枠で次のいずれか：

- `usedPercent` が20ポイント以上低下
- 前回 `usedPercent >= 15` かつ今回 `usedPercent <= 5`
- 残量が20ポイント以上増加

小さな補正はリセット扱いにしない。

## 5. 確認

一次検出後、15～30秒後に1回再取得する。

- 回復が維持：確定候補
- 元に戻る：一時的異常値として記録せず、診断ログのみ
- 再取得不能：`unconfirmed` として履歴に残すか、次回成功まで保留

## 6. 分類

### A. 通常リセット

前回の `resetsAt` が観測間隔内、または前後5分以内にあり、残量が大幅回復。

表示：`通常リセット`

### B. リセット券使用の可能性

- 予定日前の大幅回復
- `availableCount` が1以上減少
- 同じ観測間隔に券の自然失効がない

表示：`リセット券使用の可能性`

QuantaTray自身は券を使用しないため、他のCodex画面で使われた可能性を示す。

### C. 予定外リセット候補

- 予定日前の大幅回復
- リセット券の減少が確認されない
- プラン変更、枠ID変更、ウィンドウ長変更がない
- 確認再取得で回復が維持

表示：`予定外リセット候補`

説明：`予定日前に残量が回復し、リセット券の減少が確認されませんでした。理由は取得できないため推定です。`

### D. プラン／制限ポリシー変更

次を伴う場合はリセットと断定しない。

- `planType`変更
- `limitId`変更
- `windowDurationMins`大幅変更
- 複数枠構成の変更

表示：`利用枠構成の変更`

### E. データ補正・不確定

- 回復量が閾値未満
- 再確認不能
- 券詳細不足と期限切れが重なる
- アプリ停止期間が長すぎる

表示：`変化を検出（分類不能）`

## 7. リセット券失効との区別

件数減少時に、返された券の `expiresAt` が観測間隔内なら、券失効の可能性を優先する。枠回復も同時なら「券使用または失効を伴う回復」とし、確度を下げる。

## 8. 重複排除

通知と定期取得で同一イベントを二重登録しない。キー候補：

- 枠ID
- 新しい `resetsAt`
- 発生範囲
- 前後のusedPercent

60秒以内の同一変化は1件へ統合する。

## 9. 履歴表示例

```text
7/24 11:51～11:52  予定外リセット候補
残り 18% → 100% / リセット券 2 → 2

7/17 08:59～09:00  通常リセット
残り 6% → 100%

7/10 18:30～18:31  リセット券使用の可能性
残り 3% → 100% / リセット券 3 → 2
```

## 10. 保存形式

月別JSONL：

```text
history/2026-07.jsonl
```

イベント、変更観測、チェックポイントをtypeで区別する。保持期間を過ぎた月ファイルは起動時または1日1回削除する。
